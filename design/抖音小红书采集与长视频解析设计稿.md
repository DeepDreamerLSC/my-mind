
## 子设计一：抖音接入（自建 dtk 服务）

**部署**（README 详述）：

- 镜像：[Evil0ctal/Douyin_TikTok_Download_API](https://github.com/Evil0ctal/Douyin_TikTok_Download_API)，`docker compose -p dtk -f docker/compose.yml up -d --wait`，默认绑定 `127.0.0.1:8000`。
- 初始化：`.env` 写 `DTK_SECRET_KEY`（≥32 字符）等；从 api 容器日志取 setup token 建管理员；控制台生成 `X-API-Key`。
- Cookie：v5 自带身份池。优先 `--profile browser` 自动铸造身份；不可用时控制台 Identities → Import cookies 手动导入（支持 cookies.txt / key=value / 浏览器扩展导出），README 写操作路径。

**接入逻辑**：

1. `guess_platform` 判定抖音后，先走现有 HTML 抓取（快、零依赖）。
2. HTML 失败、缺正文/媒体/时长，或时长超一段式上限需要媒体时，调 `POST /api/v1/parse`（`?wait=20` 或轮询 task）。
3. **类型判定**：以 dtk 返回的 `kind`（video/图文）为准；无 API 结果时用 HTML 图集标记推断；两者皆无 → `作品类型: 未知`，不触发转写（防图文误判为视频，issue 明确要求）。
4. 媒体经 dtk 下载到缓存目录，ffprobe 校验格式与时长，转写/OCR 完成后删除。

## 子设计二：小红书接入（XHS-Downloader）

- 选型：[JoeanAmier/XHS-Downloader](https://github.com/JoeanAmier/XHS-Downloader)，13.3k star、活跃维护，支持 HTTP API 模式（`python main.py api`，默认 5556 端口，Bearer 鉴权）、Python 库、CLI。
- Cookie：可选；无 cookie 视频仅低清。按决策 2，README 写明配置网页版 cookie 的路径获取高清晰度。
- 图文：现有公开页抓取 + PP-OCRv5 OCR 为主；图片列表不全或失败时用 XHS-Downloader 兜底补全图列表再逐张 OCR。
- 视频：XHS-Downloader 下载到缓存目录，后续走与抖音一致的分段转写。
- 许可证注意：XHS-Downloader 为 GPL-3.0，只以独立进程/HTTP API 调用，不复制其代码进本仓库。

## 子设计三：长视频分段转写状态机

**分段**：

1. ffmpeg 抽音频（16k mono wav）。
2. silero-vad 标出语音区间（faster-whisper 自带 `vad_filter` 同源模型；如需独立边界则直接用 silero-vad 库），合并相邻语音为 60–180 秒的转录块，**块边界必须落在停顿处**（决策 4）。
3. 无语音区间（静默/BGM）记为「跳过区间」，计入覆盖率分母的解释但不转写。

**进度存储（收件箱笔记，决策 4）**：

```yaml
转写状态: 进行中          # 未开始/进行中/已完成/失败
转写覆盖: 720/1800秒      # 已完成块累计语音时长 / 语音总时长
转写备注: 第7块 faster-whisper 超时，下次续跑
```

正文末尾以 HTML 注释存分段清单 JSON（每块的起止秒、状态），frontmatter 只放汇总，避免 YAML 膨胀：

```html
<!-- my-mind:transcript-segments [{"s":0,"e":156,"done":true},...] -->
```

**续跑（并入后台总控日更）**：

- 总控日更新增一步：扫描 `00_收件箱/` 中 `转写状态 ∈ {未开始, 进行中}` 的视频笔记，调用 `segmented_transcribe.py --budget-seconds 900`，已完成块直接跳过。
- 媒体缓存丢失时按作品页链接 + 自建 API 重取；重取失败 → `转写状态: 失败` + 原因，转人工核验队列。
- 连续 2 次续跑零进展 → 标失败，避免无效重试占预算。

**完整判定（决策 4）**：覆盖 ≥98% → `转写状态: 已完成`，才允许内容质量升为可推送；未达标一律保持 `需继续解析`。阈值常量 `TRANSCRIPT_COMPLETE_RATIO = 0.98`。

## 子设计四：UI 演示视频的关键画面与视觉分析（已定路线，批次 5 缓后）

**路线**：ffmpeg 场景切换检测抽帧 + GLM-4.6V 视觉分析。前序批次验收后启动。

1. **抽帧**：`select=gt(scene,0.3)` 场景检测为主，长静止单镜补固定间隔（每 30s）兜底；每视频上限 12 帧，长边压到 1280px 控成本。
2. **分析**：[GLM-4.6V](https://docs.z.ai/guides/vlm/glm-4.6v)（Z.ai/BigModel API）对 UI 截图理解是强项（元素提取、界面布局），带时间戳批量送帧，要求输出结构化结果。
3. **观察与推断分离**（issue 要求）：
   - 观察 = 画面文字与界面元素的事实描述，与帧 OCR 交叉验证；
   - 推断 = 对界面变化意图、操作流程的解释，单独成段，明确标「推断」。
4. **UI 演示判定（决策 10）**：入箱时标题/文案关键词启发式（演示、操作、教程、界面、tutorial）先行标注 `作品类型: UI演示视频`；视觉模型确认随批次 5 落地；笔记 `作品类型` 用户随时可手动改写覆盖。
5. **降级备选**（无 API key 或额度不足时）：本地 PaddleOCR-VL 对帧做文档式解析，只产出「观察」不做「推断」，笔记标 `画面解析: 仅OCR降级`。

**批次 5 缓后期间的门禁行为**：关键词判为 UI 演示的作品，`画面解析=未开始` → 按规则表落在「需继续解析」，不阻塞其他模态（文案、转写）正常采集；issue #1 的 UI 演示验收项待批次 5 启动后补齐。

**成本控制**：抽帧上限、图片压缩、优先 Flash 档模型；单视频预估 <0.1 元量级，验收时实测记录。

## 子设计五：模态覆盖与门禁映射（决策 6 采用的规则）

**新增 frontmatter 字段**：

```yaml
作品类型: 口播视频        # 图文/口播视频/UI演示视频/未知
模态覆盖: 文案=完整 | 图片OCR=3/5 | 转写=83% | 画面解析=未开始
```

**规则表**（阈值集中为常量，便于调整）：

| 作品类型 | 可推送 | 需核验 | 需继续解析 |
|----------|--------|--------|------------|
| 图文 | 文案完整 且 图片OCR = N/N | OCR ≥60% 且失败页已标注待人工 | OCR <60%，或图片获取失败、文案缺失待补 |
| 口播视频 | 转写 ≥98% 且摘要/关键点已生成 | 转写 ≥98% 但文案缺失，需人工判断 | 转写 <98%（等待续跑）或转写失败 |
| UI演示视频 | 转写 ≥98% 且画面解析成功 | 画面解析部分失败但已有观察 | 转写 <98%，或视觉分析整体失败 |

**整理结果格式**：笔记内固定小节「采集整理」，含各模态覆盖表、分享文案全文、逐图 OCR（按图片序号）、时间线（口播时间点）、关键帧列表（时间戳 + 观察/推断）。仅基于文案时明确标注「仅文案，其余模态未覆盖」。
